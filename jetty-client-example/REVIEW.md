# Проверка модуля советом из пяти специалистов

Проверялись HTTP-протокол, I/O и буферы, lifecycle, производительность и
расширяемость. Реализация использует Servlet + Jetty HttpClient; Spring Security
в этот модуль не добавлен. Основное приложение с Netty сохраняется отдельно.

## Найдено и исправлено

1. **Upload и диапазон ByteBuffer.** Jetty 12.1.12 `HttpInput` сдвигает позицию
   переданного буфера. После чтения явно устанавливается диапазон прочитанных
   байтов; pooled capacity также ограничена `chunk-bytes`. Multipart, form PUT
   и chunked upload проверяются побайтно.
2. **Обратное давление и callbacks.** События обмена сериализованы асинхронно,
   без захвата Servlet-блокировки непосредственно в сетевом callback.
   Upload-буфер и response chunk освобождаются после подтверждения их использования.
   Listener жизненного цикла устанавливается до возврата из `service()`.
3. **Мелкие HTTP chunks.** Изначально каждый однобайтовый fragment приводил к
   отдельной записи. Теперь объединяются только уже доступные фрагменты:
   максимум `chunk-bytes` и 1024 фрагмента в порции. Новых данных ради batching
   не ждём. Крупный chunk не копируется ради объединения; lookahead ограничен.
4. **Отмена и переиспользуемые соединения.** Сетевая отмена идёт через исходный
   Jetty Request. Очистка локального batch не вызывает `fail()` у старого content
   source, который уже мог вернуть соединение в pool. Проверены отмена upload,
   downstream reset, timeout и shutdown с активным обменом.
5. **Промежуточные ответы.** Сохранены штатные обработчики `100/102/103`, добавлен
   fallback для остальных `1xx`, кроме `101`. Проверяются `199 → 200` и отказ
   от незапрошенного upgrade без зависшего admission.
6. **Прозрачность HTTP.** Клиент не следует redirects, не разделяет cookie store
   между пользователями и не распаковывает тело. Отключены искусственные
   Content-Type/User-Agent defaults и глобальный MVC FormContentFilter,
   способный прочитать тело до proxy Servlet.

## Расширение заголовков

`ProxyHeaderCustomizer` подключается Spring bean и упорядочивается через `@Order`.
Он получает неизменяемый снимок запроса и отдельный `ProxyHeaderEditor` с
`add`, `set`, `remove`, `values`. Request/response hooks вызываются один раз на фазу.
Доступа к телу, Servlet, URI-маршрутизации и сетевому lifecycle у hook нет.

Редактор проверяет имена и значения, закрывается после вызовов и запрещает
изменение служебных/framing-полей и описания непрозрачного тела. После hooks
повторяется очистка Connection-nominated полей. Повторные `Set-Cookie` сохраняются
отдельно. Ошибка hook даёт локальный `500` с обычной очисткой ресурсов.
Примеры `@Bean` приведены в [README](README.md#добавление-заголовков).

## Выполненные проверки

- Полная `gradle build`: **285 тестов**, без failures/errors/skips.
- Новый модуль: **40 случаев** — 20 интеграционных, 14 по расширениям заголовков,
  6 детерминированных проверок batching и владения буферами.
- Дополнительно собранный JAR прошёл 16 HTTP smoke-проверок multipart и 8 запросов
  POST/PUT в JMeter с проверкой SHA-256 тела и каждой части на upstream и клиенте.
- Runtime нового модуля не содержит Netty или Spring Security.

## Контрольные замеры

Общая машина с квотой 4 CPU, одинаковый JDK 21.0.9+10, heap 256 МиБ–1 ГиБ,
HTTP/1.1, порции 64 КиБ, одинаковый Python upstream. Для GET 8 МиБ использованы
20 клиентов, прогрев и два 15-секундных прогона на вариант в порядке A/B/B/A.
Лимит JMeter 300 rps удалён в экспериментальной копии плана вне репозитория.
Размер проверялся в каждом запросе, SHA-256 — до и после прогона.

| GET 8 МиБ | Основное приложение Netty | Новый модуль Jetty |
| --- | ---: | ---: |
| rps, два прогона суммарно | 165,4 | 190,1 |
| CPU прокси, мс/запрос | 7,86 | 5,59 |
| p95, мс | 205 | 156 |
| p99, мс | 275 | 194 |
| Ошибок | 0 | 0 |

Для ответа 64 КиБ из однобайтовых HTTP chunks обнаруженный провал **4,5 rps**
после batching сменился результатом **130,4 rps**. Контрольный Netty-прогон дал
110,8 rps. Это отдельные короткие пятисекундные прогоны с двумя клиентами.

Это диагностика общей машины, а не предел промышленной нагрузки и не сравнение
только транспорта: основное приложение также содержит commands/Resilience4j,
а пример — нет. Пулы имеют различную модель, JVM запущены по одному на вариант;
Security отсутствует в обоих. RSS/число потоков после фаз сохранены как снимки,
а не доказательство предельного расхода памяти. Точные условия, хеши JAR и
отдельные результаты находятся в [performance-results.json](performance-results.json).

## Границы заключения

Модуль остаётся самостоятельным примером. Он не заменяет контракт основного
`ProxyCall`, не добавляет Security, retries, WebSocket или HTTP/2. При добавлении
новых фильтров, body transformers или политики безопасности соответствующие
гарантии и измерения нужно проверять на этой конфигурации. Неблокирующий и
потокобезопасный характер header hooks является частью их контракта.
