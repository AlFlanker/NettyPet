**Итог после исправлений и повторной проверки:** F1–F6 и оба дополнительных
замечания закрыты; пять ролевых рецензентов не обнаружили оставшихся подтверждённых

и последующей очистки сохранены ниже.

## Подтверждённые замечания

### F1 · P2 · Просроченная попытка и поздний успех обходят общий deadline

Роли: архитектор API, SRE, инженер Netty.

Места:

- `command-support/src/main/java/com/otr/portal/command/internal/RetryTask.java:50` —
  перед `action.start()` проверяется только доставленная отмена, а не истечение времени.
- `command-support/src/main/java/com/otr/portal/command/internal/RetryTask.java:115` —
  retry запускается на общем scheduler таймаутов.
- `command-support/src/main/java/com/otr/portal/command/execution/CommandExecutor.java:273` —
  completion сначала вызывает `finishResources()`, который отменяет таймер, затем публикует результат.

Если scheduler задержан, накопленный retry с более ранним временем запуска выполняется
раньше накопленного timeout. Он может начать новое I/O уже за пределами бюджета.
Если попытка быстро завершается, она отменяет просроченный таймер и возвращает успех.

Два независимых диагностических воспроизведения выполнены вне checkout. В одном:
`timeout=80ms`, `retryWait=10ms`, scheduler задержан на 180ms, первая попытка дала
`RetryableException`, вторая вернула результат. Наблюдение:

```text
result=late-success calls=2 elapsedMs=199
CB successfulCalls=1 failures=0
```

Действия команды были неблокирующими; задерживался только scheduler, моделируя его
задержку или паузу процесса. Независимый API probe также получил вторую попытку
после истечения бюджета (`timeout=70ms`, второй start примерно через 290ms).

Воздействие: лишний побочный эффект после deadline, неверный успешный результат и
CB-статистика. В текущем HTTP-прокси `maxAttempts=1`, поэтому именно повтор запроса
там отключён. Однако при задержке таймера принятие позднего completion без сравнения
времени остаётся общей слабостью абсолютного бюджета, в том числе без retry.
Транспорт имеет собственные ограничения времени; они не заменяют контракт команды.

Исправление: создать единый scope с монотонным абсолютным deadline и состоянием
отмены до первого старта. Проверять scope непосредственно перед каждой попыткой и
при выборе итогового результата; поздний completion не должен превращать истёкший
бюджет в успех. Сигнал timeout не освобождает permit/lease до фактического cleanup.
Не выполнять произвольную логику повторной попытки в единственном потоке, который
обслуживает все deadlines; выбрать явно ограниченную модель исполнения без скрытого
переключения первого Servlet handoff на другой поток.

Дополнительный путь к той же проблеме: первая попытка может вернуть уже завершённый
retryable handle после timeout, пока внешний executor ещё не опубликовал обёртку
`RetryTask` и не доставил отмену. Отдельный блокирующий `start()` нарушает контракт;
для регрессии нужен управляемый тест гонки публикации/паузы, а не разрешение блокирующих команд.

### F2 · P2 · AssertionError после startAsync приводит к записи в уже прерванный response

Роль: специалист Servlet/Jetty.

Место: `app/src/main/java/dev/example/app/command/ProxyRequestHandler.java:33`,
затем HTTP mapping на строках 39–41.

`ProxyEngine.forwardAsync()` может вызвать `startAsync()`, затем получить `Error`
при создании exchange. Его обработчик `catch (Error)` выполняет abort и пробрасывает
ошибку. `ProxyRequestCommand` ещё не успела установить `handedToProxy=true`, поскольку
вызов не вернулся. Reactor превращает `AssertionError` в `onError` (в отличие от
JVM-fatal `VirtualMachineError`/`ThreadDeath`/`LinkageError`). Handler считает, что
response принадлежит ему, вызывает `setStatus(500)` и меняет заголовки после abort.

Воспроизведение использовало настоящий `ProxyEngine` и тестовую подмену
`NettyTransport.nextLoop()`, бросающую `AssertionError` после `startAsync()`.
Подтверждены последовательные `abortDownstream(request, fatal)` и
`response.setStatus(500)`; `handler.forward()` вернулся нормально. Старый HTTP-путь
пробрасывал `Error` без такого mapping.

Воздействие: нарушение владения Servlet response, повторное обращение после abort,
потенциально к уже завершённому или переиспользуемому контейнером объекту.

Исправление: сохранить проброс `Error` через синхронный HTTP-адаптер до любых операций
с response. Отдельно явно определить обработку `Error` в общем Reactor API;
не расширять решение до перехвата JVM-fatal ошибок как обычного fallback.

### F3 · P2 · Пользовательские registry не получают Micrometer binding

Роль: SRE.

Место: `command-support/src/main/java/com/otr/portal/command/ResilienceRegistryConfig.java:21`;
тот же шаблон используется для TimeLimiter, CircuitBreaker и Retry.

Привязка метрик находится внутри factory method с `@ConditionalOnMissingBean`.
Когда приложение предоставляет собственный registry, factory не вызывается,
поэтому при существующем `MeterRegistry` фактически используемый registry остаётся
без привязки. Автоматически созданные registry при этом публикуют метрики.

Независимый Spring probe: зарегистрированы собственный `BulkheadRegistry` и
`SimpleMeterRegistry`, импортирована `ResilienceRegistryConfig`, создан Bulkhead.
Наблюдение:

```text
sameRegistry=true
customBulkheadMeter=null
defaultRetryMeter=<meter exists>
```

Существующий тест `bindsMetricsAndHonoursAnExistingRegistry` проверяет сохранение
пользовательского registry, но наличие метрики проверяет на другом, автоматически
созданном Retry registry. Этот дефект он пропускает.

Воздействие: тихая потеря метрик при поддерживаемом переопределении registry.
JMX-диагностика текущего приложения использует прямые R4j-события и этим сценарием
не затронута.

Исправление: отделить создание default registry от binding фактически используемых
registry. Подключать метрики ровно один раз, включая пользовательские registry,
с корректным lifecycle и без двойных listeners.

Без явного описания пользователь может ошибочно считать fallback включённым в общий бюджет.

Во втором раунде дополнительно выявлены и исправлены три P2:

- **F4 — схлопывание metric ID фильтром.** `MeterFilter.ignoreTags("name")` объединял
  метрики двух профилей, а удаление одного удаляло счётчик другого. Внутренний
  `MeterAlias` сохраняет исходный ID каждой регистрации; владение считается по aliases
  и фактическим возвращённым Meter. Проверены remove/readd/remove-other и обновление
  оставшегося счётчика. Независимые SRE/API probes больше не теряют meter.
- **F5 — закрытие контекста в окне публикации composite meter.** Micrometer вызывает
  onMeterAdded до включения meter в карту; concurrent detach мог пропустить его и
  оставить ссылку на внешний MeterRegistry через закрытый child. Close очищает actual,
  освобождает даже ещё не опубликованные регистрации и переключает alias delegate на
  типизированный noop. Детерминированная регрессия и независимый SRE probe подтвердили
  отсутствие внешних ссылок и обновлений после detach.
- **F6 — потеря Reactor Context.** Внутренняя подписка `MonoCommandTask` получала пустой
  Context. Теперь `Mono.deferContextual` захватывает его для каждой подписки,
  `BaseSubscriber.currentContext()` возвращает неизменяемую копию, retry использует
  тот же контекст. `ReactorContextRegressionTest` — 7 сценариев, включая параллельных
  подписчиков и fallback. Исходный независимый probe возвращает request-123 вместо MISSING.

Aliases являются внутренними адаптерами только интерфейсов Micrometer Meter.
Политики и registry не подменяются. Proxy сохраняет ID и identity локальной регистрации,
перенаправляет измерения фактическому Meter, не закрывает пользовательский Meter и
отсоединяет delegate при освобождении. Идентичные имена/теги независимых gauge-источников
по-прежнему требуют осмысленного разделения на стороне приложения.
