# Оптимизация потокового транспорта

Дата: 20 октября 2026 года. Сохраняются три Gradle-модуля и граница композиции в `app`.

Это отчёт об этапе оптимизации. Измеренный JAR: SHA-256
`4c682a7b860588429ca1b58be2d65e42ff82b71f3e2af6f532819748bb6d69a9`.
Последующее ревью изменило idle pool и добавило JMX-диагностику; его результаты
находятся в `INDEPENDENT_REVIEW.md`. Приведённые ниже проценты относятся к прежнему
измеренному JAR и автоматически не распространяются на текущую сборку.

## Что перенесено из зрелых реализаций

Основа — явное владение буфером до callback, ограниченный спрос на чтение и отсутствие
агрегации полного тела. При реализации проверены исходники Jetty **12.1.12**:
[ProxyHandler](https://github.com/jetty/jetty.project/blob/jetty-12.1.12/jetty-core/jetty-proxy/src/main/java/org/eclipse/jetty/proxy/ProxyHandler.java),
[ServletCoreResponse](https://github.com/jetty/jetty.project/blob/jetty-12.1.12/jetty-ee11/jetty-ee11-servlet/src/main/java/org/eclipse/jetty/ee11/servlet/ServletCoreResponse.java)
и [HttpInput](https://github.com/jetty/jetty.project/blob/jetty-12.1.12/jetty-ee11/jetty-ee11-servlet/src/main/java/org/eclipse/jetty/ee11/servlet/HttpInput.java).
Использован контракт этих API; чужая реализация прокси целиком не переносилась.

| Участок | До | После |
| --- | --- | --- |
| Upload в Netty NIO | Servlet → pooled heap ByteBuf → direct ByteBuf | Для известного Jetty HttpInput: Servlet → pooled direct ByteBuf через ByteBuffer view |
| Download в Jetty | ByteBuf → scratch byte[] → Servlet output | ByteBuf → ByteBuffer view → ServletCoreResponse.write с callback |
| Множество мелких chunks | Копия каждого фрагмента в scratch/Servlet | Ограниченное объединение уже полученных мелких фрагментов в direct buffer и один callback на batch |
| Пустой ответ / HEAD | scratch выделялся при инициализации обмена | scratch не выделяется; portable-путь выделяет его только при первом body |
| План запроса | Промежуточная изменяемая копия и immutable snapshot | Фильтрация при создании финального immutable snapshot |
| Заголовки ответа | Snapshot map/list для немедленной записи | Обход скалярных значений без дополнительного snapshot |
| Планирование pump | Capturing Runnable при каждом сигнале | Один переиспользуемый Runnable на exchange |

Адаптер `JettyProxyIoAdapter` расположен в `app`, SPI `ProxyIoAdapter`/`DownstreamWriter`
— в `proxy`. Модуль `proxy` не импортирует Jetty и не знает о Resilience4j.
`resilience` продолжает работать с generic Command; итоговый cleanup транспортной
операции соединяется с временем жизни Bulkhead permit только через композицию `app`.

## Владение и обратное давление

На upload остаётся один body buffer in flight. Следующая порция читается только при
готовом Servlet input и writable upstream, после завершения предыдущей Netty write.
На download `AUTO_READ=false`, ограничены receive batch и очередь payload; следующая
запись и новое чтение разрешаются после callback текущей записи и опустошения очереди.

Queue и активная запись владеют отдельными retain исходного ByteBuf. Отмена освобождает
очередь, но активный view остаётся живым до callback успеха **или ошибки**. Именно этот
callback разрешает release. `AsyncListener.onComplete`, запрос abort и возврат из
`write()` не являются сигналами возврата памяти. Completion не доказывает получение
данных клиентом или TCP ACK.

Callback Jetty только публикует результат и ставит задачу на owner EventLoop. Он не
берёт `servletGuard`: Jetty может вызвать callback под собственным lock, и обратный
порядок захвата создавал бы deadlock. Если остановленный loop отвергает задачу,
асинхронный cleanup через GlobalEventExecutor освобождает владение без Servlet I/O.
Pending write входит в общий счётчик cleanup, поэтому admission и Bulkhead не
возвращаются раньше времени. Завершение обычного Servlet async остаётся ответственным
за финальный HTTP end marker.

Native response writer выбирается только для точного известного типа Jetty response,
когда output stream/writer ещё не выбран. Перед каждой записью состояние проверяется
повторно. ServletCoreResponse сохраняет headers/status и счётчик записанных байтов.
Обёртки никогда не распаковываются ради ускорения: для них остаётся WriteListener-путь.
Для неизвестного input остаётся heap-путь, поскольку default Servlet `read(ByteBuffer)`
может создавать промежуточный массив. Совместимость и lifetime здесь важнее предположения
о возможностях контейнера.

## Память и границы обещаний

Multipart и другие тела остаются непрозрачным потоком. Нет `getParts()`, `readAllBytes()`,
агрегации всего тела или массива размера Content-Length. Размер payload не определяет
размер отдельного буфера прокси. При этом HTTP decoder, headers, promises, views и
callbacks всё ещё создают небольшие объекты: отсутствие больших тел в heap не означает
нулевую скорость аллокаций.

Отдельно ограничена стоимость патологической HTTP-фрагментации. Префикс очереди из
двух и более полных фрагментов меньше 1 KiB объединяется, если его суммарный размер
не превышает `chunk-bytes`. Destination buffer запрашивается ровно этого размера;
allocator может округлить внутреннюю резервацию. Следующий крупный или не поместившийся
фрагмент не копируется частично. Каждое такое объединение уменьшает число native writes,
не добавляя ожидания или upstream read-ahead. Одиночное маленькое событие отправляется
сразу. Порог 1 KiB — выбранная эвристика, а не доказанный оптимум для любого трафика.

Для Jetty upload устранена потребность именно этого пути в Netty heap arena. Это не
гарантирует отсутствие больших heap arrays во всей JVM: portable input, другие компоненты
и настройки allocator могут создавать backing slabs. Direct pooling также резервирует
память вне Java heap. TLAB, G1 humongous objects и direct memory — разные категории;
large/humongous allocation не следует называть «большим объектом внутри TLAB».

Прямой input всё ещё копирует данные из входного содержимого Jetty в назначенный буфер.
TLS, socket buffers, kernel I/O и возможная внутренняя обработка контейнера не исчезают.
Здесь устранены конкретные промежуточные копии между библиотеками, а не заявлен полный
zero-copy сетевого обмена.

## Проверки

На этапе оптимизации `clean build --rerun-tasks`: **155 тестов**, app 56, proxy 81, resilience 18;
ошибок и пропусков нет. 27 новых тестов относительно предыдущей версии проверяют:

- Direct upload и отсутствие scratch для пустого переносимого ответа.
- Один native write in flight; запрет следующего read до возврата владения.
- Удержание body и flush в cleanup/admission; отмену с поздним успехом и ошибкой.
- Callback под чужим lock, синхронный callback и callback после остановки owner loop.
- Неизменность переданного view, fallback и повторную проверку Servlet output state.
- Реальный Jetty: остановившийся клиент/RST, восстановление admission и целостность
  следующего бинарного ответа; сохранение преобразования тела Servlet wrapper.
- Повторные заголовки, регистр имён, фильтрацию и неизменность snapshots.
- Объединение мелких фрагментов: целостность, ограничение размера, сохранение исходного
  крупного фрагмента, удержание destination buffer после отмены и немедленная отправка
  одиночного короткого события.

Независимое ревью транспорта, адаптера, метаданных и композиции не выявило блокирующих
дефектов. Это подтверждение проверенных сценариев, а не доказательство любой гонки
или производительности под произвольной нагрузкой.

## Измерения

Протокол и standalone harness находятся в [`perf/README.md`](perf/README.md).
Измеряются две заранее собранные версии приложения при одинаковых параметрах.
Полный сравнительный результат, SHA-256 JAR и свидетельства JFR находятся
в [`perf/results.json`](perf/results.json). Здесь байты Java heap allocations на запрос
по ThreadMXBean, округлённые до целого:

| Сценарий | До, B/request | После, B/request | Изменение в этом прогоне |
| --- | ---: | ---: | ---: |
| HEAD, 5000 запросов | 30 593 | 13 441 | −56,06% |
| Upload 1 MiB, 1024 запроса | 78 962 | 59 573 | −24,56% |
| Download 1 MiB, 1024 запроса | 96 208 | 71 377 | −25,81% |
| 64 KiB ответа в однобайтовых chunks, 64 запроса | 2 809 242 | 2 810 232 | +0,035%; практически прежний уровень |

Условия: JDK 21, G1, heap 256 MiB, четыре клиента, два Netty loops, HTTP/1.1 loopback,
одинаковый harness и отдельный прогрев каждой фазы. Прокси не загружается body-массивами
fixture: клиент и upstream находятся в отдельном Python-процессе. Целостность тел
проверяется SHA-256. JFR включён только в нужных окнах; leak detection выключен только
в эксперименте, а в Gradle-тестах включён paranoid.

ThreadMXBean учитывает аллокации surviving platform threads, кроме управляющего потока
измерителя. Исчезнувших потоков в обоих прогонах нет; baseline HEAD создал один новый
поток, учтённый с нуля, остальные фазы — без новых потоков. Потоки, родившиеся и
завершившиеся между снимками, этим методом не учитываются. Счётчики включают overhead
framework/JFR; это не измерение retained heap, direct memory или RSS. JFR samples
помогают найти стеки, но не служат точным счётчиком объектов или байтов.

Первый кандидат без объединения мелких фрагментов был отклонён: этот сценарий потреблял
36 683 564 B/request, в 13,1 раза больше baseline. После исправления — 2 810 232.
Локальная диагностическая скорость того же сценария: baseline 149,42 req/s,
неудачный кандидат 12,46, исправленный 210,24. Это подтверждает устранение конкретного
узкого места; один короткий замер с Python fixture не доказывает устойчивый прирост
production throughput. Остальные проценты также относятся к данному сравнению,
а не к любому профилю нагрузки.

Отдельная first-touch JFR-запись до основного прогрева зарегистрировала у baseline
два Netty heap-arena `byte[]` по **4 194 320 B** из upload-пути, вне TLAB. При фактическом
G1 region 1 MiB это humongous objects. У финального кандидата такие события в этом
окне отсутствовали, что согласуется с переходом Jetty upload на direct buffers.
Это не доказательство отсутствия крупных массивов во всём приложении или других
режимах: portable upload и другие компоненты сохраняют собственные allocator paths.

Полный production GO по-прежнему требует целевых SLO, HTTPS load/soak, контроля heap,
direct memory/RSS и испытания остановки под трафиком. Сравнение с предыдущей версией
не означает победу в benchmark над Jetty ProxyHandler, NGINX или Envoy: такие замеры
в этой работе не выполнялись.
