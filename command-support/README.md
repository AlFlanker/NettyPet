# command-support

Команды на Project Reactor с Resilience4j 2.4.0: semaphore Bulkhead, общий TimeLimiter,
CircuitBreaker и явно разрешённый Retry. Требуются Java 21 и Gradle 8.14.3.

```bash
./gradlew :command-support:test
./gradlew build
```

`Command<T>.execute()` возвращает холодный `Mono<T>`. Создание команды и вызов
`execute()` не начинают работу. Каждая подписка получает отдельное выполнение;
повторяемость самого источника остаётся обязанностью реализации команды.

Контекст Reactor подписчика доступен внутри `doExecute()` через `Mono.deferContextual`
и сохраняется при повторных попытках и fallback. Разные подписчики одной команды
получают собственный контекст; он не сохраняется в общем реестре политик.
Низкоуровневый `CommandAction`/`CommandTask` с `CompletionStage` является обычным
callback API: передавайте нужные данные в ресурсную команду явно, например при её
создании внутри `Mono.deferContextual`. Автоматического переноса произвольных
`ThreadLocal` этот контракт не обещает.

## Обычная реактивная операция

Наследуйте `AbstractResilienceCommand<T>` и реализуйте `getCommandName()`,
`doExecute(): Mono<T>` и `fallbackOnError(Throwable): Mono<T>`. Конструктор принимает
`CommandResilienceDecorator` и неизменяемые `CommandProperties`. Вызов `doExecute()`
отложен до подписки и допуска политик; синхронная ошибка тоже проходит через fallback.

Этот вариант подходит, когда завершение или отмена подписки означает окончание
владения ресурсами операции. Если отмена только запрашивает асинхронную очистку,
используйте ресурсную команду.

## Операция с асинхронной очисткой

`AbstractResourceCommand<T>` сохраняет тот же `execute(): Mono<T>` и fallback,
но вместо `doExecute()` реализуется `doStart(): CommandTask<T>`.

```java
@Override
protected CommandTask<Result> doStart() {
    ExternalCall call = client.start();
    return new CommandTask<>() {
        public CompletionStage<Result> completion() {
            return call.resultAfterCleanup();
        }
        public void cancel(CancellationReason reason) {
            call.requestCancellation(reason);
        }
    };
}
```

`completion()` подтверждает **фактическое освобождение всех ресурсов**, в том числе
после ошибки или отмены. `cancel(reason)` неблокирующий, идемпотентный и не считается
подтверждением очистки. Если `doStart()` бросает исключение до возврата handle,
реализация должна сама убрать всё, что успела создать.

Timeout может вернуть ошибку/fallback раньше очистки. Слот Bulkhead и ссылка на
поколение конфигурации остаются занятыми до `completion()`. Отмена подписки передаётся
задаче; shutdown декоратора запрашивает отмену активных задач. Для явного наблюдения
используйте `CommandResilienceDecorator.start(context, action)`: `CommandExecution`
разделяет `result()`, `terminated()` и `cancel()`. `terminated()` подтверждает cleanup
и возврат слота. Отмена копии future, полученной из stage, не отменяет операцию.

Не подписывайтесь на долгоживущую операцию самостоятельно внутри `doExecute()`
и не возвращайте горячий источник, работающий до допуска политик.

## Политики и retry

`CommandProperties.builder()` задаёт:

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `timeout` | 3 секунды | Бюджет исходной операции, включая повторы и ожидания; fallback имеет отдельный lifecycle |
| `maxConcurrency` | 50 | Число живых операций, включая очистку |
| `circuitBreakerConfig` | 50%, окно 10, OPEN 5 секунд | Полная политика CB, включая predicates результата/ошибки |
| `maxAttempts` | 1 | Всего попыток, включая первую |
| `replayable` | false | Явное подтверждение возможности повторения |
| `retryWaitDuration` | 500 мс | Пауза между разрешёнными повторами |

`maxAttempts > 1` требует `replayable=true`. Повторяются только
`RetryableException`; произвольные ошибки, отказы admission и отмена не должны
повторять побочный эффект. Новая попытка начинается после очистки предыдущей и
укладывается в общий бюджет. Fallback вызывается после завершения политики повторов.
Источник обязан заново создавать операцию и данные каждой попытки.

### Границы fallback

`fallbackOnError()` выполняется **вне** timeout, Bulkhead, CircuitBreaker и Retry
исходной операции. Fallback может начаться сразу после timeout, когда исходная
операция ещё очищает ресурсы и продолжает занимать свой слот. После cleanup этот
слот возвращается независимо от того, завершился ли fallback. Длительность fallback
не продлевает бюджет исходной операции и не меняет её sample в CircuitBreaker.

Для fallback с внешним I/O задавайте собственные timeout и admission, например
отдельную защищённую команду с другим именем политики. Не считайте наличие fallback
ограничением его параллелизма. Отмена downstream-подписки отменяет активный fallback;
она сама по себе не вызывает новый fallback. Ошибка fallback передаётся подписчику,
а не запускает fallback рекурсивно.

Для потокового Servlet request автоматический retry отключён: прочитанное тело
невозможно воспроизвести, а повтор частично отправленного POST может повторить действие.
Само подключение Reactor не превращает одноразовую операцию в повторяемую.

CB наблюдает результат общей политики TimeLimiter. В стандартной конфигурации
timeout считается ошибкой, локальная отмена и отказ запуска исключены из статистики.
Приложение может явно задать другую классификацию через `circuitBreakerConfig`.

Общий бюджет измеряется монотонными часами и не сбрасывается между попытками.
Перед запуском попытки и принятием результата проверяется тот же deadline:
задержка timer scheduler не разрешает просроченный retry или поздний успех.
Первая попытка запускается на вызывающем потоке, что сохраняет синхронный Servlet
handoff. Последующие попытки начинают работу в отдельном пуле из двух потоков
с ограниченной очередью на 256 задач; таймер только планирует их запуск.
Переполнение пула даёт локальный `CommandNotExecutedException`, а не новый вызов
upstream. При отмене или shutdown отложенные задачи не начинают операцию, даже если
их Runnable ещё находился в очереди. Эти потоки запускают короткий неблокирующий
`doStart()`/подписку, а не обслуживают сетевой обмен целиком.

## Реестр и lifecycle

Имя команды обозначает ограниченный набор логических операций, а не произвольный URI
или идентификатор клиента. У одного имени одна неизменяемая политика. Изменение
свойств при существующем имени отклоняется; для смены политики сначала дождитесь
очистки и удалите старую запись.

`CommandConfigRegistry.acquire(context)` выдаёт `Lease` со стабильным `holder()`.
Исполнитель удерживает lease от допуска до cleanup, включая retry. Идемпотентный
`close()` освобождает ссылку. `clearCache(prefix)` и `clearAllCaches()` атомарно
отклоняются, если затронутая запись используется; чужие записи внешних R4j-реестров
не удаляются. Для долговременных подписок на события/диагностику также удерживайте
lease, чтобы смена поколения не оставила наблюдатель на старом лимитере.

Общий `CommandResilienceDecorator` закрывается владельцем один раз при остановке.
`doStart()`, `cancel()`, источники при подписке, callbacks и listeners должны быть
короткими и неблокирующими. Блокирующий вызов до возврата handle нельзя безопасно
остановить таймером. Не завершающая cleanup зависшая операция продолжает занимать слот.

## Spring и метрики

Пакет `com.otr.portal.command` подключается явно, если находится вне component scan:
импортируйте `ResilienceRegistryConfig`, `CommandConfigRegistry` и
`CommandResilienceDecorator`. Конфигурация сохраняет пользовательские R4j registry
beans. При наличии `MeterRegistry` привязываются Micrometer-метрики; без него модуль
тоже запускается. Actuator и HTTP management endpoints модуль не подключает.

Binding подключается к фактически внедрённым registry, включая пользовательские
beans, независимо от создания defaults. Контекст владеет своей привязкой к
`MeterRegistry`; закрытие освобождает её без закрытия пользовательских registry
и без повторного добавления R4j listeners при повторном использовании. Независимые
registry, публикующие в один `MeterRegistry`, должны различать имена/теги профилей:
одинаковые metric ID имеют обычную семантику Micrometer с одним источником gauge.

`holder()` содержит фактически используемые R4j-объекты. Их listeners не должны
блокировать или бросать исключения. Не меняйте конфигурацию лимитеров напрямую
во время выполнения; используйте управляемую смену поколения реестра.

В NettyPet `ProxyRequestCommand` использует ресурсный API, а `ProxyCommands` удерживает
общую политику и обслуживает JMX-диагностику. Общий deadline потока там намеренно
исключён из CB: медленный клиент не доказывает отказ backend. Ошибка соединения,
upstream header timeout и upstream 5xx по-прежнему учитываются как ошибки.
