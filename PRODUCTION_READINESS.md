# Решение седьмого технического рецензента

Дата: 20 октября 2026 года.

## Вердикт

**GO для контролируемых изолированных preproduction-испытаний; production GO пока
не выдан.** Полная сборка `clean build --rerun-tasks` прошла успешно:
168 тестов; ошибок и пропусков нет. Разбивка: app — 65,
proxy — 85, resilience — 18. В последнем независимом ревью добавлены 13 тестов
к предыдущим 155. Результат зафиксирован в `verification.json`.
Нагрузочный профиль, SLO и ограничения production-окружения не были заданы,
нагрузочные и длительные soak-испытания не проводились. Подменять их числом
юнит-тестов было бы неверным инженерным решением.
Локальный сравнительный эксперимент аллокаций описан в `OPTIMIZATIONS.md` и `perf/`;
он выполнен для версии до последнего ревью и не заменяет проверку текущего JAR.
Последнее решение и подтверждённые исправления: `INDEPENDENT_REVIEW.md`.
Условия испытаний и перехода к ограниченному canary: `TRIALS.md`.

Седьмая роль объединяет HTTP/security, Netty/concurrency, Servlet/Jetty, SRE,
проектирование API и Resilience4j. Она независимо проверила выводы шести ролей
по исходникам и тестам. Это техническое ревью агентов, не внешняя сертификация.

## Оценка работы коллег

| Вывод предыдущего ревью | Решение седьмого рецензента |
| --- | --- |
| Закрывающийся TLS-канал нельзя возвращать в ACTIVE pool | Принят. `closeFuture → release` устраняет причину ошибки; управляемые promises подтверждают порядок и удержание admission |
| Гонку shutdown/schedule нельзя считать отказом upstream | Принят. Локальная отмена сохраняется; недоступный scheduler не запускает команду и не загрязняет CB |
| `CALL_FINISHED` нужен только после cleanup запущенной команды | Принят. Событие и возврат permit согласованы; неиспользованный permit не создаёт ложного завершения |
| Границы трёх модулей сохранены | Принят. Композиция находится в app; proxy и resilience не зависят друг от друга |
| Достаточность прежних доказательств для production GO | Предыдущий отчёт корректно исключал нагрузочные гарантии. Дополнительно выявлены пробелы реального TLS и проверки молчащего backend как причины открытия CB |

## Список доработок и внесённые изменения

### Последнее независимое ревью: idle pool и наблюдаемость

Новый RED-тест подтвердил повторную выдачу idle-канала, который начал асинхронное
закрытие, но ещё оставался ACTIVE. Перед close теперь ставится постоянный признак
RETIRING, а pool health checker исключает такой канал. Две регрессии проверяют
отказ в повторной выдаче и сохранение здорового соединения при отменённом idle timer.

В app добавлена read-only JMX диагностика транспорта, Bulkhead/CB/TimeLimiter и локального
lifecycle. Закрыты пробелы raw-upstream framing, границ очереди и остановки приложения
с активными потоками. Полное описание и доказательства — в `INDEPENDENT_REVIEW.md`.

### Повторное решение после оптимизации I/O

Проверены direct upload, передача исходного response view в Jetty, точный момент
release после callback, late callback после остановки owner loop и сохранение
Servlet wrappers. Композиция Resilience4j по-прежнему удерживает permit до фактического
cleanup. Независимый рецензент не нашёл блокирующих дефектов в итоговом патче.

Первый эксперимент выявил регрессию native write на каждом однобайтовом HTTP chunk:
резко выросло число аллокаций и операций записи. Этот вариант отклонён. Добавлено
ограниченное объединение минимум двух уже полученных мелких фрагментов, уменьшающее
число записей без задержки ожидания. Четыре отдельные регрессии проверяют содержимое,
предел размера, отмену и немедленную отправку одиночного события. Исходный неудачный
замер сохранён в сравнительном отчёте, чтобы причина изменения была проверяемой.

Контракт адаптера привязан к проверенному Jetty 12.1.12. При обновлении контейнера
нужно повторить проверки bridge/callback и сетевые регрессии. Допуск остаётся
поэтапным: снижение аллокаций не подтверждает целевые SLO и длительную
стабильность под нагрузкой. Детали, ограничения памяти и результаты — в `OPTIMIZATIONS.md`.

### P2: молчащий backend не открывал CircuitBreaker

После полной отправки запроса backend мог бесконечно ждать с ответом. Срабатывал
только общий deadline, который намеренно исключён из статистики CircuitBreaker:
общая длительность также зависит от клиента. Поэтому повторные такие 504 не
отсекали backend через circuit, хотя Bulkhead ограничивал количество зависших операций.

Добавлен `proxy.response-headers-timeout` (по умолчанию 10 секунд). Он запускается
после успешной отправки последнего request content и отменяется при финальных
response headers либо завершении обмена. Промежуточные 1xx его не продлевают.
Timeout даёт `UPSTREAM_FAILURE/504`, который существующая политика app считает
ошибкой upstream. Общий deadline по-прежнему игнорируется.

Таймер не измеряет клиентский upload и streaming body ответа. Если общий бюджет
команды истечёт раньше, диагностировать отдельный header timeout не получится;
настройки должны оставлять достаточно времени для этой фазы. Модули не связываются
ради сравнения их настроек: политика бюджетов остаётся ответственностью app.

Регрессии проверяют момент запуска таймера, его отмену на финальных headers,
удержание разрешений до cleanup, повторные зависания с открытием circuit и отказ
следующему запросу без обращения к backend. Отдельно проверяется streaming body,
который продолжается дольше header timeout после своевременных headers.

### Пробел доказательств: настоящий HTTPS

Добавлены сетевые проверки с Jetty и локальным `HttpsServer`, свежими сертификатами
с SAN и штатным JDK trust manager. Production TLS не подменяется trust-all реализацией.

- Доверенный сервер: первая порция body доступна до завершения ответа; завершённое
  соединение можно повторно использовать.
- Доверенный сертификат с неверным hostname: 502 до передачи HTTP-запроса backend.
- Недоверенный сертификат: 502 до передачи HTTP-запроса backend.
- Отмена TimeLimiter посреди TLS stream: неполный downstream response завершается
  ошибкой чтения; оба admission-лимита восстанавливаются; следующий запрос использует
  новое TLS-соединение.

Тестовые truststore-настройки восстанавливаются после тестов. Закрытые ключи и
сертификаты генерируются во временном каталоге и не входят в поставляемый проект.

### Уточнение наблюдаемой семантики

Документация больше не обещает, что любой timeout результата команды изменит HTTP
на 504. `CommandExecution.result()` может получить timeout уже после завершения HTTP,
пока продолжается cleanup. Отправленный ответ в этом случае не изменяется.
`terminated()` остаётся сигналом освобождения ресурсов; Bulkhead не возвращает
слот преждевременно. Это уточнение контракта, а не новая утечка ресурсов.

## Что нужно измерить до полного production GO

| Проверка в целевом окружении | Критерий допуска |
| --- | --- |
| Номинальная и пиковая нагрузка с реальными размерами тел, HTTPS и долей долгих потоков | Достигнуты заранее согласованные throughput, p99 и error budget; лимиты соответствуют CPU, памяти и возможностям backend |
| Устойчивая нагрузка и длительный soak после прогрева | Нет неограниченного роста heap, direct memory, открытых FD и pending операций; максимальная память укладывается в лимит процесса |
| Медленные upload/download, disconnect, молчащий и восстанавливающийся backend | Очереди остаются ограниченными, Bulkhead отказывает без ожидания; после cleanup admission возвращается к исходному уровню, CB допускает успешные probes |
| Остановка приложения под трафиком | Новые запросы прекращают допускаться, активные операции завершаются/отменяются в установленный shutdown budget, upstream-каналы не остаются открытыми |

Конкретные SLO задаёт владелец сервиса. Эти проверки требуют реального профиля трафика и
целевого окружения; локальная сетевая регрессия не измеряет его производительность.
Перед canary эксплуатация должна видеть latency/errors, занятые admission-слоты,
состояния CB, события TimeLimiter и память/FD; локальный JMX bridge уже есть в app,
сбор и экспорт на стенде подключаются средствами платформы. Порог остановки canary и rollback определяются
согласованным error budget, а не числом успешно выполненных тестов.

## Сохраняемые ограничения

Приложение не содержит аутентификации: при необходимости она должна предшествовать
proxy-фильтру либо обеспечиваться доверенным входным контуром. Upstream выбирается
из доверенного allowlist. HTTP/2 upstream, CONNECT, WebSocket, gRPC и trailers не
поддерживаются. Сетевые тесты покрывают HTTP/1.1 downstream; HTTP/2 downstream
не является проверенным режимом эксплуатации.

Processor, Command.start/cancel и подписчики событий обязаны быть неблокирующими.
Один CB защищает общую логическую группу `/proxy`; независимым backend-группам нужны
отдельные ограниченные профили в app. Автоматических retries потоковых тел нет.

Результат ревью не равен полной проверке безопасности всех транзитивных зависимостей.
Перед выпуском следует сверить разрешённый runtime dependency graph с актуальными
advisories в используемом процессе управления зависимостями; веб-поиск не заменяет
такую проверку. Версии, запрошенные пользователем, сохранены.
